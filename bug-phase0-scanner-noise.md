# Bug: Phase 0 auto-scanner emits low-signal findings that cost the reviewer a full proposal

## Context

Session `01a0155a` (spec 10), Phase 0. The spec review prompt listed "8 potential findings"; 4 were auto-generated by `findIssues` (`src/reviewer.ts`) and were noise for this spec (e.g. "I/O without error handling" on a pure string-building prompt function, subjective-threshold hits on boilerplate phrases). The LLM reviewer had to spend its first `negotiate_propose` call explicitly dismissing them ("The 4 auto-generated findings: 1 an...") before reaching the 4 real findings — a full round-trip of reviewer tokens and user wait time on findings it was never meant to act on.

## Observed problem

1. `findIssues` (`src/reviewer.ts:92-96`) pattern-matches the spec text (subjective thresholds, I/O keywords, vague phrases) and returns findings with no confidence or applicability signal.
2. The Phase 0 prompt presents them as "potential findings" alongside the instruction to "check for ambiguities, missing edge cases" — the reviewer cannot tell which are mechanical pattern hits (verify-before-acting) and which are structural (act on them).
3. Observed cost: one extra full proposal (dismissing 4, confirming 3-4) before the spec could be approved. In spec 09's run the same class of noise appeared (the reviewer's F-C disposition had to rule on scanner findings the spec author had already dismissed in its Findings log).

The scanner is doing its job (it catches real issues in other specs) — the defect is that its output is **unlabeled**, so the reviewer treats it as peer evidence instead of leads.

## Proposed fix

1. Tag each finding with its origin: `source: "scan" | "structure"` (scan = pattern hit, structure = e.g. missing acceptance criteria / interface gaps detected by the structural passes).
2. In the Phase 0 review prompt, group and label them: "Auto-scan leads (verify before acting): …" vs "Structural findings (act on these): …". The reviewer's instruction becomes: confirm or dismiss each scan lead in one line; analyze structural findings in depth.
3. Cap scan leads in the prompt (e.g. top 5 by category diversity) with a count of the rest, so a noisy spec can't flood the prompt.
4. *Scope question for Phase 0:* is labeling enough, or should scan leads be demoted to a separate `loop-debug`-only output (not in the review prompt) unless the structural passes find nothing? Labeling is the smaller change; demotion changes the Phase 0 contract.

## Acceptance

- `findIssues` findings carry a `source` field (type-level: `Finding.source: "scan" | "structure"`); existing structural findings all tagged `structure`, pattern-based ones `scan`.
- The Phase 0 prompt renders the two groups under distinct headers (test pins the prompt shape for a spec with both kinds).
- Scan leads beyond the cap are summarized as a count, not listed (test for a spec with >5 scan hits).
- `npm test` green; existing reviewer tests updated for the new field.

## Evidence

Session `01a0155a`, 14:51:18 Phase 0 prompt: "Spec content (4 potential findings)" — the scanner's 4 auto findings (I/O-without-errors, subjective-threshold hits) for a spec about a completion-report string builder; reviewer's first proposal (14:54:51) spent its opening section dismissing them before the 3 real blockers.
