# implement-spec-format-validation

## Problem

Verified current state as of writing: Phase 0 review
(`src/reviewer.ts:85` `analyzeSpec`) runs 5 heuristic checks on the spec
text:

1. `detectVaguePhrases` — flags "properly", "correctly", "obviously", etc.
2. `detectSubjectiveThresholds` — flags "within N rounds", "on first attempt"
3. `detectMissingErrorHandling` — flags I/O keywords without error mentions
4. `detectConflictingStatements` — flags same concept with different values
5. `detectMissingTestStrategy` — flags specs with no test strategy section

None of these check whether the spec **follows the template** in
`docs/spec-authoring.md`. A spec that is missing the "Acceptance Criteria"
section, the "Inventory" section, or the "Target" section passes Phase 0
review (the heuristics don't look for section headers). The LLM Reviewer
agent may notice, but there's no structural guarantee.

The template defines these required sections:
- Problem
- Target
- Interface (optional if no signature change)
- Behavior
- Inventory
- Test Strategy
- Scope lines
- Acceptance Criteria
- Dependencies
- Findings log

A hand-written spec (not generated by `/spec`) can omit any of these and
the loop will still run. The Tester and Writer then work from an incomplete
contract, which is the exact failure mode the template was designed to
prevent.

## Target

Before the LLM Reviewer runs, a structural validator checks that the spec
contains the required section headers. Missing sections produce a **hard
finding** (severity: blocker) that the user must address before the loop
proceeds. The validator is a pure string check — no LLM, no heuristics.
It checks for markdown headers matching the template's section names.

The validator runs BEFORE `analyzeSpec`. If any required section is missing,
the findings include a blocker finding per missing section, and the loop
stays in Phase 0 review (the user must fix the spec or the finding must be
explicitly rejected via `negotiate_review`).

## Interface

New function in `src/reviewer.ts`:

```ts
export function validateSpecStructure(specText: string): Finding[];
```

Returns an array of `Finding` objects. One finding per missing required
section. Each finding has:
- `category: "Missing section"`
- `title: "Missing required section: <name>"`
- `ambiguity: "The spec does not contain a '<name>' section. The template requires it."`
- `interpretations: []` (no interpretations — it's a structural check, not an ambiguity)
- `recommendation: "Add a '<name>' section to the spec."`

Required sections (case-insensitive header match):

| Section | Header pattern | Required |
|---|---|---|
| Problem | `# <verb>-<object>` or `## Problem` | yes |
| Target | `## Target` | yes |
| Behavior | `## Behavior` | yes |
| Inventory | `## Inventory` | yes |
| Test Strategy | `## Test Strategy` | yes |
| Scope lines | `## Scope lines` | yes |
| Acceptance Criteria | `## Acceptance Criteria` | yes |
| Dependencies | `## Dependencies` | yes |
| Findings log | `## Findings log` | yes |
| Interface | `## Interface` | no (optional if no signature change) |

The title line (`# <verb>-<object>`) is checked as: the spec must start with
a `# ` header. If it doesn't, a finding is produced.

**Modified function** in `src/reviewer.ts`:

```ts
export function analyzeSpec(specText: string): SpecAnalysis;
```

Becomes:

```ts
export function analyzeSpec(specText: string): SpecAnalysis {
  const structural = validateSpecStructure(specText);
  const findings = [...structural, ...findIssues(specText)];
  return { findings, reasons: ["Phase 0 is the baseline"] };
}
```

Structural findings come first (they're blockers, not ambiguities).

## Behavior

**Decision table** for `validateSpecStructure`:

| Row | Condition | Output |
|---|---|---|
| 0 | `specText` is empty or whitespace | `[]` (let the existing empty check in `findIssues` handle it) |
| 1 | No `# ` title line at start | 1 finding: "Missing title" |
| 2 | Missing `## Target` | 1 finding: "Missing required section: Target" |
| 3 | Missing `## Behavior` | 1 finding: "Missing required section: Behavior" |
| 4 | Missing `## Inventory` | 1 finding: "Missing required section: Inventory" |
| 5 | Missing `## Test Strategy` | 1 finding: "Missing required section: Test Strategy" |
| 6 | Missing `## Scope lines` | 1 finding: "Missing required section: Scope lines" |
| 7 | Missing `## Acceptance Criteria` | 1 finding: "Missing required section: Acceptance Criteria" |
| 8 | Missing `## Dependencies` | 1 finding: "Missing required section: Dependencies" |
| 9 | Missing `## Findings log` | 1 finding: "Missing required section: Findings log" |
| 10 | All present | `[]` |

Multiple missing sections → multiple findings, one per section, in the
order listed above.

**Header matching rules**:
- Case-insensitive: `## target`, `## TARGET`, `## Target` all match.
- Trailing whitespace is trimmed.
- The header must be a markdown H2 (`## `), not H1 (`# `) or H3 (`### `).
- The header line must start with `## ` (two hashes + space). A line like
  `##Target` (no space) does NOT match.
- Code blocks (``` ... ```) are ignored — a `## Target` inside a code block
  is not a section header.

**Interaction with existing findings**:
- Structural findings are prepended to the heuristic findings.
- They have no `interpretations` array (empty), so the Reviewer prompt
  shows them as "add this section" rather than "choose an interpretation."
- The user can reject a structural finding via `negotiate_review` if they
  believe the section is genuinely not needed (e.g., a bug-fix spec with no
  signature change can reject "Missing Interface").

**Quirks list**:
- The existing `findIssues` has an early return: `if (!specText.trim())
  return []`. The new `validateSpecStructure` also returns `[]` for empty
  text. The two are consistent.
- `detectMissingTestStrategy` (existing heuristic) checks for the string
  "test" in the spec. The new structural check checks for the `## Test
  Strategy` header. Both can fire: a spec with "test" in the body but no
  `## Test Strategy` header gets both a heuristic finding AND a structural
  finding. This is intended — the structural finding is the blocker, the
  heuristic is the soft nudge.

**Intended shifts**:
- Specs that previously passed Phase 0 with missing sections will now get
  blocker findings. This is the intended behavior change.
- The `/spec` command already generates well-formed specs with all sections.
  Specs written by `/spec` will not be affected.

**Ownership**:
- `src/reviewer.ts` owns `validateSpecStructure` and the modified
  `analyzeSpec`.
- `test/reviewer.test.ts` (existing) asserts the new findings.
